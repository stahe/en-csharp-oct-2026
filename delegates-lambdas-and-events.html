    7. Delegates, Lambdas, and Events

    In the 2008 course, this chapter followed the one on Windows Forms graphical user interfaces: events were first introduced in the context of buttons and forms, and then students learned how to create events in their own classes. The chapter on graphical user interfaces has been removed from this version of the course. We therefore begin directly with the concept that underlies the entire mechanism: the delegate, that is, an object that references one or more methods. All examples are console programs.

    Over the past twenty years, delegates have become one of the most widely used tools in the language. Writing them has become considerably simpler with lambda expressions (C# 3), which we have already used—without going into detail—with LINQ in Chapter 5: [Where(n => n > 5)] passes a lambda—and thus a delegate—to the method [Where]. This chapter explains what lies behind this syntax. It concludes with events, which are also based on delegates. The graphical user interfaces of .NET (Windows Forms, WPF, .NET MAUI) as well as the web frameworks are based on this mechanism: a button click or the arrival of a HTTP request are signaled to subscribed methods.

    The programs in this chapter are single-file applications located in the [07-delegues] folder. They are run using [dotnet run delegues-NN.cs].

    7.1. Predefined Delegate Types

    7.1.1. The concept of a delegate

    A delegate type describes a model (also called a prototype or signature) of a method: the types of its parameters and the type of its return value. A variable of a delegate type can then reference any method that matches this model and execute it.

    The .NET framework defines numerous delegate types. The oldest is [EventHandler], used by all the events we’ll discuss at the end of this chapter. It is defined as follows:

    1
    public delegate void EventHandler(object? sender, EventArgs e);

    The keyword [delegate] makes [EventHandler] a delegate type. This type denotes a method pattern:

    • whose first parameter is an object of type [object?] (the object that triggered the event, possibly [null]);
    • whose second parameter is an object of type [EventArgs] (information about the event);
    • returning no result ([void]).

    A method corresponding to the model defined by [EventHandler] could be as follows:

    1
    static void Afficher(object? sender, EventArgs e) { ... }

    To create an object of type [EventHandler] that references this method, you can write:

    1
    EventHandler gestionnaire = new EventHandler(Afficher);

    or, more simply:

    1
    EventHandler gestionnaire = Afficher;

    In this second notation, the method name [Afficher] (a method group, since a method can have multiple overloads) is automatically converted by the compiler into a [EventHandler] object: this is method group conversion, which has been possible since C# 2. The compiler selects, from among the overloads of [Afficher], the one that matches the delegate’s signature. The delegate is then executed as a method: [gestionnaire("programme", EventArgs.Empty)].

    7.1.2. The Generic Delegates Func, Action, and Predicate

    Before generics (C# 2), you had to define a delegate type for each method signature. Today, the framework provides generic delegate types that cover almost all needs:

    Delegate type
    Methods Referenced
    [Action]
    No parameters, no return value: [void M()]
    [Action<T1, ..., T16>]
    1 to 16 parameters, no results: [void M(T1 p1, ...)]
    [Func<TResult>]
    No parameters, one result: [TResult M()]
    [Func<T1, ..., T16, TResult>]
    1 to 16 parameters, a result of the type [TResult] (always the latest type)
    [Predicate<T>]
    one parameter, a Boolean result: [bool M(T p)]
    [Comparison<T>]
    two parameters of the same type, an integer result: [int M(T x, T y)]

    [Predicate<T>] and [Func<T, bool>] describe the same signature but are two different types: [Predicate<T>] is derived from NET 2 and is used by the methods of [List<T>] and [Array] ([FindAll], [RemoveAll], [Exists]…), whereas LINQ, which was introduced with .NET 3.5, uses [Func<T, bool>].

    7.2. Defining Delegate Types

    Predefined types are often sufficient, but you can define your own delegate types. The statement:

    1
    public delegate int Operation(int n1, int n2);

    defines a type called [Operation], which represents a method template that takes two integers and returns an integer. Compared to [Func<int, int, int>], the type [Operation] has a name that describes its purpose, and its parameters have names ([n1], [n2]) that development tools display.

    A variable [op] of type [Operation] is used to store a list of methods corresponding to the [Operation] model: this is referred to as a multicast delegate.

    • A method of type [f] is stored in the variable [op] using [op = new Operation(f)] or, more simply, [op = f];
    • To add a method [g] to the list of already registered methods, write [op += g];
    • To remove a method [h] that is already registered, enter [op -= h];
    • The [n = op(n1, n2)] statement executes, in the order in which they were registered, all methods registered in [op], using the parameters [n1] and [n2]. The returned result [n] is that of the last method executed.

    The 2008 course indicated that it is not possible to obtain the results of all methods. It is possible, but not with a single call: you must iterate through the list of methods returned by [GetInvocationList] and call them one by one. In practice, methods registered in a multicast delegate most often return [void].

// We define an object of type Operation to store methods in it
// We register the static method Increase
Operation op = Calculs.Augmenter;
// Execute the delegate

// Create an object c1 of type Calculations

// Register the Add method of c1 in the delegate

// Execute the delegate object

// The "Subtract" method of c1 is registered in the delegate

n = op(2, 3);
Console.WriteLine($"n={n}");

// Registering two methods in the delegate (multicast delegate)
op = c1.Ajouter;
op += c1.Soustraire;
// Executing the delegate object: retrieving the result of the last method
n = op(10, 4);
Console.WriteLine($"n={n}");
// The results of all methods along with the invocation list
foreach (Operation methode in op.GetInvocationList().Cast<Operation>())
{
    Console.WriteLine($"{methode.Method.Name} -> {methode(10, 4)}");
}
// Removing a method from the delegate: the result may be null (type Operation?)
Operation? reste = op - c1.Soustraire;
// Execute the delegate if it is not null
if (reste is not null)
{
    n = reste(1, 1);
    Console.WriteLine($"n={n}");
}
// Removing the last method: the delegate becomes null
Operation? vide = reste - c1.Ajouter;
Console.WriteLine($"vide est null : {vide is null}");
// ?.Invoke executes the delegate only if it is not null
Console.WriteLine($"vide?.Invoke(1, 1)={vide?.Invoke(1, 1)}");

    A delegate is an immutable object: the operations [+] and [-] (and therefore [+=] and [-=]) do not modify the existing delegate; they create a new one. This property will be important when dealing with events.

    Form
    Example
    typed parameters, block body

    Parameters are either all typed or all untyped: you cannot mix the two. In this course, we will use lambdas rather than anonymous methods, which are now only useful in rare cases.

    7.5. Event Handling

    7.5.1. The .NET Event Model

    Delegates are used to define events. A [C1] class can define a [Evt1] event as follows:

    • A delegate type is defined within or outside the class [C1]:
    1
    delegate void Evt(T1 param1, T2 param2, ...);
    • The class [C1] defines a field of this delegated type:
    1
    public Evt? Evt1;
    • When an instance [c1] of the class [C1] wants to signal an event, it executes its delegate [Evt1] by passing it the parameters defined by the type [Evt]. All methods registered in the delegate [Evt1] are then executed with these parameters. It can be said that they have been notified of the event [Evt1];
    • if a [c2] object that uses the [c1] object wants to be notified of the [Evt1] event of the [c1] object, it registers one of its methods, [c2.M], with the delegate [c1.Evt1]. Its method [c2.M] will then be executed every time the event [Evt1] occurs on the object [c1]. It can also unsubscribe when it no longer wishes to be notified;
    • since the delegate [c1.Evt1] can register multiple methods, different [ci] objects can register with [c1.Evt1] to be notified of the event.

    In this scenario, we have:

    • a class that signals (also called “publishes” or “emits”) an event;
    • classes that are notified of this event. They are said to subscribe to the event;
    • a delegate type that defines the signature of the methods that will be notified of the event. These methods are called event handlers.

    This is the Observer design pattern: the emitter does not know its subscribers; it simply notifies them.

    The .NET framework defines a standard signature for an event delegate:

    1
    public delegate void MonEventHandler(object? sender, EventArgs e);
    • [sender]: the object that triggered the event;
    • [e]: an object of type [EventArgs] or a derived type, which provides information about the event;
    • By convention, the name of the delegate type ends with [EventHandler].

    It also defines a standard way to declare an event of type [MonEventHandler] in a class:

    1
2
3
4
5
    public class C1
{
    public event MonEventHandler? Evt1;
    ...
}

    The field [Evt1] is of the delegate type. The keyword [event] restricts the operations that can be performed on it:

    • From outside the [C1] class, only the operations [+=] and [-=] are permitted. This prevents the subscribed methods from being overridden or deleted (by mistake, for example, by writing [=] instead of [+=]) by other objects. You can only subscribe ([+=]) or unsubscribe ([-=]);
    • only the class [C1] can execute the delegate, that is, trigger the event: [Evt1?.Invoke(this, e)].

    If you try, from outside the class, to write [c1.Evt1 = null;] or [c1.Evt1(null, EventArgs.Empty);], the compiler responds with: [error CS0070: L'événement 'C1.Evt1' ne peut apparaître qu'à gauche de += ou -= (sauf quand il est utilisé à partir du type 'C1')] (in English: [The event 'C1.Evt1' can only appear on the left hand side of += or -= (except when used from within the type 'C1')]).

    Rather than defining a delegate type for each event, we use the predefined generic delegate:

    1
    public delegate void EventHandler<TEventArgs>(object? sender, TEventArgs e);

    The type [TEventArgs] is that of the second parameter, the object that describes the event. With this generic delegate, the declaration of a [X] event in a [C] class follows the recommended pattern below:

    • define a type [XEventArgs] derived from [EventArgs] to encapsulate information about the [X] event;
    • define an event of type [EventHandler<XEventArgs>] in the [C] class;
    • define in the [C] class a protected and virtual method [protected virtual void OnX(XEventArgs e)] intended to publish the [X] event to subscribers. It is virtual so that a derived class can modify how the event is published.

    In 2008, the type [TEventArgs] was required to derive from [EventArgs] (constraint [where TEventArgs : EventArgs]). This constraint was removed in .NET Framework 4.5: any type is acceptable, including a [record]. However, by convention, we continue to derive from [EventArgs]. Note that a [record] cannot be derived from [EventArgs]: a [record] can only inherit from another [record] (error: [CS8864 : Les enregistrements peuvent uniquement hériter d'un objet ou d'un autre enregistrement]). We will therefore use a regular class.

public static class Outils
{
     // filters a sequence with a predicate: the equivalent of Where
    public static IEnumerable<T> Filtrer<T>(IEnumerable<T> source, Func<T, bool> predicat)
    {
        foreach (T element in source)
        {
            if (predicat(element))
            {
                 // the element is returned to the caller; the iteration will resume here
                yield return element;
            }
        }
    }
}

public static class Extensions
{
     // extension members (C# 14) of IEnumerable<T>
    extension<T>(IEnumerable<T> source)
    {
         // Filter as an extension method: we reuse Outils.Filtrer
        public IEnumerable<T> Filtrer(Func<T, bool> predicat) => Outils.Filtrer(source, predicat);

         // transforms each element: the equivalent of Select
        public IEnumerable<TResult> Transformer<TResult>(Func<T, TResult> transformation)
        {
            foreach (T element in source)
            {
                yield return transformation(element);
            }
        }
    }
}

    7.8. Conclusion

    Key takeaways from this chapter:

    • A delegate is an object that references one or more methods with a given signature. The predefined types [Func<>], [Action<>], and [Predicate<T>] usually eliminate the need to define your own delegate types;
    • lambda expressions allow you to write the method right where you create the delegate. They capture the variables surrounding them (be careful with loops [for]);
    • A delegate can replace a single-method interface, offering greater flexibility;
    • an event is a delegate protected by the keyword [event]: you subscribe to it using [+=], unsubscribe using [-=], and only the class that declares it triggers it, using [Evt?.Invoke(this, e)];
    • LINQ is built on methods that accept delegates, and EF Core is built on expression trees.

    Delegates will be discussed again in the following chapters: a task ([Task.Run]) executes a delegate in another thread (Chapters 8 and 9), and the ASP.NET Core web services associate lambdas with HTTP addresses (Chapter 13).

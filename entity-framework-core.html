    11. Entity Framework Core

    The previous chapter showed how a .NET application communicates with a database through a ADO.NET connector: a connection is opened, SQL commands are written, the result rows are read column by column, and they are copied into objects. This process of copying—from rows to objects and from objects to the [INSERT], [UPDATE], and [DELETE] commands—is repetitive. It can be automated using a tool: an ORM (Object-Relational Mapper). This chapter introduces Microsoft’s Entity Framework Core (EF Core).

    The 2008 course did not mention ORM: it merely mentioned, at the conclusion of its chapter on databases, “third-party data access frameworks” (NHibernate, iBatis) and LINQ. Entity Framework was released a few months later (in 2008, with .NET 3.5 SP1), and in 2012 the author dedicated a course to it, titled “Introduction to Entity Framework 5 Code First Through Examples.” This chapter is entirely new. It builds on the sample database from the articles in Chapter 10 and concludes with version 7 of the tax calculation application, whose [dao] layer uses EF Core.

    11.1. What is a ORM?

    11.1.1. Objects and Tables

    A C# application works with objects: an item has a name, a price, and a stock level; an order has a customer and a list of line items, each of which refers to an item. A relational database stores this same information in tables: one row in the [articles] table per item, one row in the [commandes] table per order, with the relationships between rows expressed by foreign keys. The two worlds do not quite align:

    • an object directly references other objects ([commande.Client]); a row contains the primary key value of another row ([ClientId]);
    • an object can contain a collection ([commande.Lignes]); a table contains only single values; the collection is represented by the rows of another table that point to the order;
    • the C# types ([string], [decimal], [DateOnly], [bool]) and the types SQL ([varchar(30)], [decimal(10,2)], [date], [tinyint(1)]) are not the same;
    • objects are queried using C# (and LINQ), and tables are queried using SQL.

    A ORM bridges the two worlds. We define the mapping between classes and tables (the model) once and for all; it then takes care of:

    • translating LINQ queries written in C# into SQL and [SELECT] commands;
    • creating objects from the read rows (this is called materialization);
    • storing the read objects and detecting those that have been modified, added, or deleted;
    • generate the commands [INSERT], [UPDATE], and [DELETE] that reflect these changes in the database;
    • and, if necessary, to create and update the database schema (tables, columns, indexes) based on the classes.

    The architecture of an application that uses EF Core with MySQL is as follows:

    • [1]: the application. Its [dao] layer no longer communicates with a ADO.NET connector but with EF Core, via a [DbContext] object and LINQ requests;
    • [2]: EF Core, independent of SGBD: template, translation of LINQ requests, change tracking, migrations;
    • [3]: the EF Core provider specific to SGBD (here Pomelo for MySQL): it recognizes the SQL dialect of SGBD and its column types;
    • [4]: the ADO.NET connector for SGBD, the one from Chapter 10 (MySqlConnector): EF Core does not replace ADO.NET; it uses it;
    • [5]: the SGBD.

    11.1.2. EF Core and Entity Framework 6

    There are two products named Entity Framework:

    • Entity Framework 6 (EF 6), the original product, designed for the .NET Windows Framework (since version 6.3, it also works on .NET Core and its successors). It is still maintained but is no longer under active development;
    • Entity Framework Core, a complete rewrite released in 2016 with .NET Core. It runs on all .NET platforms (Windows, Linux, macOS) and is the version that receives all new features. Its version number follows that of .NET: EF Core 8 with .NET 8, EF Core 9 with .NET 9, EF Core 10 with .NET 10.

    For a new application, we use EF Core. Both products have similar API versions ([DbContext], [DbSet<T>], LINQ, migrations), so what is stated here remains largely true for EF 6.

    11.1.3. Providers

    EF Core accesses a SGBD through a provider, distributed in a NuGet package. Microsoft provides the providers for SQL Server, SQLite, and Azure Cosmos DB; the others are written by the SGBD publishers or by the community: [Npgsql.EntityFrameworkCore.PostgreSQL] for PostgreSQL, [Oracle.EntityFrameworkCore] for Oracle, [Pomelo.EntityFrameworkCore.MySql] and [MySql.EntityFrameworkCore] (from Oracle) for MySQL. We are using Pomelo, the most widely used MySQL provider, which is based on the [MySqlConnector] connector from Chapter 10.

    A provider is compiled for a specific version of EF Core: Pomelo 9 works with EF Core 9, and Pomelo versions are often released several months after those of EF Core. The course uses EF Core 9.0.0 and Pomelo 9.0.0, on .NET 10. This combination works: EF Core 9 targets .NET 8 ([net8.0]), and a library compiled for .NET 8 works without modification on .NET 10. The transition to EF Core 10 will be accomplished by changing the package version numbers; the code in this chapter should then work without modification, apart from a few minor details in the generated SQL. However, in the section on LINQ, we will encounter a minor incompatibility between EF Core 9 and the C# 14 compiler.

    11.1.4. Code First and Database First

    The EF Core model (the mapping between classes and tables) can be built in two ways:

    • Code First: You write the C# classes, and EF Core derives the database schema from them, which it can create on its own and then update as the application evolves (migrations). This is the approach taken in this chapter and in the author’s 2012 course;
    • Database First: The database already exists, and you generate the classes from its schema using the [dotnet ef dbcontext scaffold] command. This is the approach used for applications that need to work with an existing database. The generated code is similar to what we would write by hand.

    11.3. The model

    EF Core builds its model from entities in three steps:

    • First, it applies its conventions;
    • it supplements or corrects them using the annotations (attributes) applied to the entities;
    • finally, it applies the configuration written in C# in the [OnModelCreating] method of the context: the API flow.

    11.3.1. The Conventions

    We saw the essentials of these in the first example:

    • any public property with a [get] getter and a [set] (or [init]) setter is stored in a column of the same name;
    • the property [Id] or [<Entité>Id] is the primary key; if it is an integer, its values are generated by SGBD;
    • the table name is that of the [DbSet] property of the context (or, failing that, that of the class);
    • a property of a nullable type ([int?], [DateOnly?], [string?]) results in a column [NULL]; a property of a non-nullable type ([int], [decimal], [string] when nullable reference types are enabled) results in a [NOT NULL] column;
    • a property that references another entity, or a collection of entities, defines a relationship (we’ll cover this later).

    11.3.3. Nullable types and columns NULL

    Nullable reference types (C# 8, enabled by [<Nullable>enable</Nullable>] in the course projects) have an impact on the model: EF Core reads the nullability annotations generated by the compiler. A [string] property results in a [NOT NULL] column, and a [string?] property results in a [NULL] column. In a project where nullable types are not enabled, all text columns accept [NULL], except those marked [Required].

    You must therefore choose the type of each property carefully: it expresses both a C# code rule (“this value may be missing”) and a database constraint. For a required property, two notations are common:

    private static bool Filtre(EventId id, LogLevel niveau) =>
        id == RelationalEventId.CommandExecuted || id == RelationalEventId.CommandError
        || id == RelationalEventId.TransactionStarted
        || id == RelationalEventId.TransactionCommitted || id == RelationalEventId.TransactionRolledBack;

     // displays an event
    private static void Afficher(EventData donnees)
    {
        switch (donnees)
        {
            case CommandExecutedEventData commande:
                AfficherCommande(commande.Command);
                break;
            case CommandErrorEventData erreur:
                AfficherCommande(erreur.Command);
                Console.WriteLine("    SQL> -- échec de la commande");
                break;
            case TransactionEventData when donnees.EventId == RelationalEventId.TransactionStarted:
                Console.WriteLine("    SQL> -- début de transaction");
                break;
            case TransactionEventData when donnees.EventId == RelationalEventId.TransactionCommitted:
                Console.WriteLine("    SQL> -- transaction validée (COMMIT)");
                break;
            case TransactionEventData:
                Console.WriteLine("    SQL> -- transaction annulée (ROLLBACK)");
                break;
        }
    }

     // Displays the SQL command (indented) followed by its parameters
    private static void AfficherCommande(DbCommand commande)
    {
         // Empty lines are ignored
        foreach (string ligne in commande.CommandText.Split('\n').Select(l => l.TrimEnd()).Where(l => l != ""))
        {
            Console.WriteLine("    SQL> " + ligne);
        }
        if (commande.Parameters.Count > 0)
        {
            var parametres = commande.Parameters.Cast<DbParameter>()
                .Select(p => $"{(p.ParameterName.StartsWith('@') ? "" : "@")}{p.ParameterName}={p.Value}");
            Console.WriteLine($"    SQL> -- paramètres : {string.Join(", ", parametres)}");
        }
    }

    11.5.2. The States of an Entity

    Tracking changes is based on the state of each entity, a value from the [EntityState] enumeration:

    State
    Meaning
    [Detached]
    The object is not tracked by the context (created by [new] and not yet added, or deleted from the database)
    [Added]
    The object has been added to the context ([Add]): [SaveChanges] will insert it into the database
    [Unchanged]
    The object was read from the database (or saved) and has not been modified since
    [Modified]
    At least one property has been modified: [SaveChanges] will send a command [UPDATE]
    [Deleted]
    The object has been marked for deletion ([Remove]): [SaveChanges] will send a command [DELETE]

    Note the work cycle with EF Core: entities are read, modified like ordinary objects, added, and deleted, then [SaveChanges] is called, which sends all necessary commands to the database in a single batch. The context acts as a “unit of work.” A context is a lightweight object designed for a short lifespan: a unit of work, such as a HTTP query in a web application. The same context is not used throughout the entire life of an application, as it would accumulate tracked entities.

    11.6.2. IQueryable and expression trees

    How can the same lambda be executed in C# on a list and translated to SQL on a [DbSet]? Chapter 7 provided the answer: a [DbSet<T>] implements the [IQueryable<T>] interface, whose methods [Where], [OrderBy], [Select]... receive not delegates ([Func<T, bool>]) but expression trees ([Expression<Func<T, bool>>]). The compiler transforms the lambda [a => a.StockActuel < a.StockMinimum] into a data structure that describes it (“ comparison [<] of property [StockActuel] and property [StockMinimum] of parameter [a]”); EF Core traverses this structure and produces the equivalent SQL. A method such as [Regles.EnRupture] appears in the tree only as a method call, whose code cannot be analyzed: hence the error.

    Operators are composed: a query can be built in stages, with each stage returning a new [IQueryable<T>], and only the final execution ([ToList], [First], [Count], [foreach]...) sends a SQL command:

    11.6.3. An incompatibility between EF Core 9 and C# 14

    In the program [Linq], the list [noms] was declared as type [List<string>] rather than [string[]], with a comment referencing this paragraph. With an array, the query [contexte.Articles.Where(a => noms.Contains(a.Nom))] compiles but fails at runtime with a [InvalidOperationException] error (“An exception was thrown while attempting to evaluate a LINQ query parameter expression”). In fact, C# 14 has made the conversion of an array to [ReadOnlySpan<T>] (the type introduced in Chapter 5) an implicit language conversion, which also applies to the object on which an extension method is called. For an array, the call [noms.Contains(...)] therefore now refers to the extension method [MemoryExtensions.Contains(ReadOnlySpan<T>, T)] rather than [Enumerable.Contains(IEnumerable<T>, T)]: This is evident from examining the lambda’s expression tree, and the same program compiled in C# 13 ([<LangVersion>13</LangVersion>]) finds [Enumerable.Contains] and works. EF Core 9, released before C# 14, does not recognize this method: it attempts to evaluate the array conversion to [ReadOnlySpan<string>] to make it a parameter SQL, which fails (the internal exception is a [ArgumentException] thrown by the expression tree interpreter). EF Core 10, released alongside C# 14, supports this syntax. With EF Core 9, you can work around the issue by using a list, as shown here, or by writing [((IEnumerable<string>)noms).Contains(a.Nom)]. This is the only issue encountered in this chapter when using EF Core 9 with .NET 10.

    11.8. Migrations

    11.8.1. The Principle

    So far, the database has been created by [EnsureCreated], after being deleted by [EnsureDeleted]. This is impossible for a live application: its database contains data that must be preserved when the model evolves (a new column, a new table). Furthermore, [EnsureCreated] can only create a database that does not exist: if the database already exists with tables, it does nothing, even if the model has changed.

    Migrations address this need. A migration is a C# class, generated by the [dotnet ef] tool, that describes the transition from one version of the model to the next: its [Up] method applies the change (create a table, add a column), while its [Down] method reverts it. The database contains a table named [__EFMigrationsHistory], where EF Core records the migrations that have been applied to it; this allows it to know which ones still need to be applied.

    11.10. Transactions and Concurrency

    11.10.1. Transactions

    Chapter 10 introduced transactions: a set of operations that either all succeed or all fail. With EF Core, there are two key points to note:

    • [SaveChanges] is transactional: if it sends multiple commands, it executes them within a transaction. If any one of them fails, none are committed, and [SaveChanges] initiates a [DbUpdateException];

    11.10.2. Optimistic Concurrency

    Two users read the same item, which has a stock of 10. The first user sells one item and updates the stock to 9. The second user, who read the stock before this update, sells three items and updates the stock to 7: the first user’s sale is lost. This is the problem of lost updates.

    One solution would be to lock the row for the entire duration of each user’s operation (“pessimistic” concurrency): this blocks other users, sometimes for a long time. EF Core implements optimistic concurrency: nothing is locked, but at the time of the commit, the system verifies that the row has not been modified since it was read. To do this, one or more properties are designated as concurrency tokens: EF Core adds the condition “the token still has the value read” to the [WHERE] clause for the [UPDATE] and [DELETE] statements. If the command does not modify any rows, it means another user has already processed them: EF Core initiates a [DbUpdateConcurrencyException].

    11.12. Context and Dependency Injection

    The previous examples created their contexts using [new]. In a layered application, and in all ASP.NET Core applications, contexts are created by the dependency injection container introduced in Chapter 6. EF Core provides two extension methods of [IServiceCollection] for this purpose:

    • [AddDbContext<T>(options => ...)] registers the [T] context with a “scoped” lifetime: the container creates a context per scope, provides it to all services within that scope that request it, and releases it at the end of the scope. In a web application, a scope is created for each request HTTP: each request has its own context, which corresponds to the context’s unit of work;
    • [AddDbContextFactory<T>(options => ...)] registers a context factory, [IDbContextFactory<T>], whose method [CreateDbContext] creates a new context on each call. It is used in long-running services (singletons), which cannot maintain the same context throughout the application’s lifetime, and in parallel processing, which requires one context per task.

    In both cases, the lambda receives a *[DbContextOptionsBuilder] and configures the context as *[OnConfiguring]* did; the context must have a constructor that accepts a *[DbContextOptions<T>], such as the one in the *[ArticlesContext]* class.

    11.14. Conclusion: ADO.NET, Dapper, or EF Core?

    We now have two ways to access a database: ADO.NET (Chapter 10) and EF Core (this chapter). There is a third, intermediate method that is widely used: Dapper, a small library (a “micro-ORM”) that adds extension methods to the ADO.NET connection. These methods execute a hand-written SQL query and automatically convert the rows in the result into objects: [connexion.Query<Article>("SELECT * FROM articles WHERE Prix > @prix", new { prix = 200 })]. You write the SQL, and Dapper handles mapping the columns to properties.

     
    Strengths
    Weaknesses
    ADO.NET
    Full control over SQL; performance; no dependencies
    a lot of repetitive code (parameters, reading columns); SQL in strings, not checked by the compiler
    Dapper
    SQL hand-written but without copy code; performance similar to ADO.NET
    No change tracking or generation of [INSERT]/[UPDATE]; no migrations
    EF Core
    LINQ queries verified by the compiler; change tracking; relationships; migrations; independent of SGBD
    an additional layer to understand; SQL generated to be monitored; less suitable for complex bulk processing

    The following guidelines can be proposed:

    • EF Core is suitable for most management applications: a model of interconnected entities, operations for reading and updating entities, and a schema that evolves with the application. It is the default choice for ASP.NET Core applications;
    • ADO.NET, or Dapper, is suitable when you want precise control over the SQL executed: complex reporting queries, stored procedures, processing very large volumes, or an existing database with a schema poorly suited to an object-oriented model;
    • These approaches can be combined: an application can use EF Core for the most part and hand-written SQL code—using [FromSql], [SqlQuery], or Dapper—for a few critical queries. EF Core also provides access to the ADO.NET connection it uses ([contexte.Database.GetDbConnection()]).

    In any case, knowing about ORM does not eliminate the need to understand SQL and how SGBD works: the log of executed SQL commands, which we have displayed throughout this chapter, is the primary tool for verifying what EF Core actually does.
